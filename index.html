    Day 2 of 14

    Arrays & Hashing II

    More of the same core idea — a hashmap keyed by something you compute, not just the raw value.

    currently examining match / resolved seen / checked

    Concept: keying by a computed signature

    Day 1's hashing checked "have I seen this exact value?" Day 2 pushes the idea further: instead of hashing the raw value, you hash something you compute from it — a sorted string, a frequency count, a running product — and use that computed key to group, rank, or reconstruct.

    This works because a well-chosen key collapses everything that should be treated the same into one bucket. Sort a word's letters and every anagram of it lands on the identical key. Count a word's letters and you get an even cheaper signature. The hash map is still doing O(1) lookup/insert — the new skill is designing the key.

    Space/time stays close to O(n·k) for n items of size k (the cost of computing each key), a small constant-factor tax over O(n) for the win of avoiding an O(n²) pairwise comparison.

    Reach for a computed key when: the problem asks you to group items that are "equivalent" under some transformation (anagrams, same digit sum, same remainder), or to answer a query in one pass by precomputing running totals to each side (prefix/suffix products, prefix sums). Interviewers will often ask "can you avoid division?" for products-except-self — the answer is prefix/suffix passes, not one division pass.

    Group Anagrams

    Given an array of strings, group the anagrams together.

    groups — keyed by sorted letters

    The trick: anagrams share the same letters, so sorting a word's letters gives every anagram of it the same key. Group by that key in one pass — O(n·k log k) for words of length k.

    Top K Frequent Elements

    Given an array and an integer k, return the k most frequent elements.

    counting frequencies

    counts, ranked by frequency

    The trick: count frequencies first, then you only care about the top k of them. Sorting by count is O(n log n) and fine for most interviews; the optimal O(n) version bucket-sorts by frequency instead of sorting.

    Product of Array Except Self

    Return an array where each element is the product of all other elements — without using division.

    left pass — product of everything before i

    running product

    The trick: the product-except-self at index i is (everything to its left) × (everything to its right). Compute left-products in one pass, then multiply in right-products in a second pass over the same array — no division needed.

    Day 3 of 14

    Two Pointers

    Two indices moving toward each other (or in lockstep) over sorted or symmetric data — trading a nested loop for a single pass.

    currently examining match / resolved seen / checked

    Concept: two pointers closing in

    Hashing trades memory for speed. Two pointers trades a second pass for a smarter single one: when an array is sorted (or can be treated as sorted, like a palindrome read from both ends), the answer often lives at the boundary between "too small" and "too big" — so walk two indices toward each other instead of checking every pair.

    Why it's correct, not just fast: at each step you eliminate one index from consideration entirely. If nums[left] + nums[right] is too small, nums[left] paired with anything ≤ nums[right] is still too small — so left can only move up. That's what turns an O(n²) nested loop into a single O(n) sweep, O(1) extra space (aside from the output).

    The same shape reappears any time you're comparing "one end" against "the other end" and monotonicity (sortedness) lets you discard a whole side per step.

    Reach for two pointers when: the input is sorted (or you sort it first) and you're looking for a pair/triple hitting a target sum, or you're comparing an array/string against its own reverse. Common follow-up: dedupe results (skip over repeated values after a match) and handle the "3Sum" style extension by fixing one pointer and two-pointering the rest.

    Valid Palindrome

    Given a string, return true if it reads the same forwards and backwards, ignoring case and non-alphanumeric characters.

    s

    The trick: walk from both ends inward. Skip characters that aren't letters or digits. Compare the rest case-insensitively — one mismatch means it's not a palindrome; pointers crossing means it is.

    Two Sum II — Input Array Is Sorted

    Given a sorted array and a target, return the 1-indexed positions of the two numbers that add up to target.

    numbers (target = 6, sorted)

    The trick: because it's sorted, a hashmap isn't even needed. Start pointers at both ends — if the sum is too big, the right pointer is carrying too much, move it left; if too small, move the left pointer right.

    3Sum

    Given an array, return all unique triplets that sum to zero.

    nums, sorted

    The trick: sort first. Fix one number (i), then run the Two Sum II two-pointer pattern on the rest of the array looking for a pair that cancels it out. Skip over duplicate values for i, and for left/right after a match, so you don't return the same triplet twice.

    Day 4 of 14

    Sliding Window

    A window of indices that grows and shrinks over an array or string — instead of re-scanning from scratch every time.

    currently examining match / resolved seen / checked

    Concept: the sliding window

    A sliding window is two pointers that both move forward, never backward, tracing out a contiguous subarray or substring. Instead of recomputing a property (a sum, a set of characters, a max) from scratch for every possible window, you maintain it incrementally: expand the right edge and update, shrink the left edge and update.

    The efficiency comes from amortized cost: each index enters the window once (right pointer) and leaves once (left pointer), so total work across the whole scan is O(n) even though you're implicitly considering O(n²) possible windows. The window's size is either fixed (given directly) or variable, growing until it breaks some constraint and then shrinking until it's valid again.

    Space is typically O(1) to O(k) for whatever you're tracking inside the window (a running max, a small frequency table over at most 26 letters, etc).

    Reach for a sliding window when: you see "contiguous subarray/substring", "longest/shortest ... with at most/exactly k ...", or "maximum ... within a window of size k". A frequent interview trap: forgetting the window can only grow when it's still valid — shrink from the left the moment the constraint is violated, don't reset from scratch.

    The trick: grow the window by moving right one step at a time. The moment you see a character already inside the window, jump the left edge to just past its last occurrence — the window only ever moves forward.

    Longest Repeating Character Replacement

    The trick: a window is valid as long as (window size − count of its most frequent character) ≤ k — that's how many characters you'd need to replace. Grow the window; when it stops being valid, shrink from the left instead of resetting.

    Day 5 of 14

    Stack

    Last in, first out. Whenever "the most recent unmatched thing" matters, a stack is almost always the answer.

    currently examining match / resolved seen / checked

    Concept: LIFO and the monotonic stack

    A stack solves problems whose structure is "the most recent unresolved thing matters most" — last in, first out. Matching brackets is the canonical case: the most recently opened bracket must be the next one closed. Push what's open/unresolved; pop and check when you see something that should close it.

    A monotonic stack is the same idea aimed at a different question: "for each element, what's the next element that breaks a trend?" (next greater, next warmer day, next taller building). You keep the stack's values in increasing (or decreasing) order by popping off anything the current element invalidates — and the pop is exactly the answer for whatever you just popped, e.g. "it took (i - j) days to warm up."

    Both run in O(n) time: even though there's a nested-looking while loop doing the popping, each element is pushed once and popped at most once, so total pushes+pops across the whole array is O(n).

    Reach for a stack when: you need to match/nest pairs (brackets, tags), undo the most recent operation, or you're asked "for each element, find the next one that is greater/smaller/further/warmer" — that phrasing is the monotonic-stack tell. A common follow-up: implement getMin() in O(1) alongside push/pop by keeping a parallel stack of running minimums.

    Valid Parentheses

    Given a string of brackets, return true if every bracket is closed in the right order.

    s

    stack (top on the right)

    The trick: push opening brackets. On a closing bracket, it must match whatever is currently on top of the stack — if it doesn't (or the stack's empty), it's invalid. Valid only if the stack is empty at the end.

    Min Stack

    Design a stack that supports push, pop, top, and getMin — all in O(1).

    operations

    main stack (top on the right)

    min-tracking stack — top is always the current minimum

    The trick: keep a second stack alongside the main one. Push onto it whenever the new value is ≤ its current top (a new minimum, or tying the old one); pop from it whenever you pop that same value off the main stack. Its top is always the current min in O(1).

    Daily Temperatures

    Given daily temperatures, return for each day how many days you'd wait for a warmer one.

    temperatures

    stack — indices waiting for a warmer day (top on the right)

    The trick: keep a stack of indices whose answer you don't know yet. Whenever today's temperature beats the one on top of the stack, that day finally got its answer — pop it and record the gap. This is a monotonic (decreasing) stack.

    Binary Search

    Any time you can rule out half the remaining space with one check, you've got O(log n) instead of O(n) — even when the array isn't fully sorted.

    currently examining match / resolved seen / checked

    Concept: halving the search space

    Binary search isn't really about sorted arrays — it's about any question where you can evaluate a midpoint and, from the answer, throw away half the remaining possibilities with certainty. On a sorted array that's trivial: compare the target to the middle element and discard the half that can't contain it.

    The pattern generalizes to "rotated" or otherwise partially-ordered structures: at least one half of any split is still properly sorted, so you can always tell which half to search by comparing boundary values, even though the whole array isn't monotonic. It also generalizes past arrays entirely — "binary search on the answer" applies binary search to a range of possible answers, checking feasibility at each midpoint (not covered here, but the same halving logic).

    Each halving is O(1) work, and you halve log₂(n) times, giving O(log n) time and O(1) space — a huge win over O(n) linear scanning once n is large.

    Reach for binary search when: the input is sorted, or "sorted then rotated," or the problem says "find the minimum x such that..." (search on the answer). A classic pitfall: off-by-one loop bounds — decide up front whether your invariant is lo <= hi or lo < hi and stay consistent, and use lo + (hi - lo) / 2 to avoid overflow in languages where it matters.

    Binary Search

    Given a sorted array and a target, return its index, or -1 if it isn't there.

    nums (target = 9)

    The trick: look at the middle element. If it's the target, done. If it's smaller, the target must be to the right — discard the left half. If bigger, discard the right half. Repeat.

    Search in Rotated Sorted Array

    A sorted array has been rotated at an unknown pivot. Find the target's index in O(log n).

    nums (target = 0)

    The trick: at least one half (left of mid, or right of mid) is always properly sorted, even after rotation. Figure out which half is sorted, check if the target falls in that half's range — if yes, search there; if no, search the other half.

    Find Minimum in Rotated Sorted Array

    Find the minimum element in a rotated sorted array, in O(log n).

    nums

    The trick: compare nums[mid] to nums[hi]. If nums[mid] > nums[hi], the minimum must be to the right of mid (mid itself can't be it). Otherwise, the minimum is at mid or to its left. Narrow until lo == hi.

    Linked List

    No random access — only "what's next." Most linked list tricks come down to a small number of pointers you move carefully, in the right order.

    currently examining match / resolved seen / checked

    Concept: pointers instead of indices

    A linked list has no random access — you can't jump to index i, only follow .next. Every technique here is about keeping a small, fixed number of pointers (prev/curr/next, or slow/fast) and moving them through the list in lockstep, rewiring .next links as you go instead of building a new structure.

    The fast/slow (tortoise-and-hare) pointer pair is the key trick to internalize: advancing slow by 1 and fast by 2 each step means if the list has a cycle, fast eventually laps slow and they meet — impossible without a cycle. The same pair finds the middle of a list in one pass (when fast hits the end, slow is at the midpoint), which is how reordering and palindrome-checking problems get solved without extra memory.

    All of these run in O(n) time and O(1) extra space — the entire point is to avoid the O(n) space of copying values into an array first.

    Reach for pointer manipulation when: you see "reverse", "find the middle", "detect a cycle", or "merge/reorder" applied to a linked list. Pitfall to watch for: losing the reference to the rest of the list before you've saved it (always grab next before you overwrite .next), and remembering a dummy head node sidesteps annoying "is the list empty / am I at the head" special cases when merging or removing nodes.

    Reverse Linked List

    Reverse a singly linked list in place.

    reversed so far

    The trick: keep three pointers — prev, curr, next. Save curr.next before you overwrite it, point curr back at prev, then slide all three pointers forward one node.

    Merge Two Sorted Lists

    Merge two sorted linked lists into one sorted list.

    list 1
    list 2
    merged result

    The trick: walk both lists with a pointer each. At every step, attach whichever current node is smaller to the result and advance only that pointer. When one list runs out, attach the rest of the other.

    Linked List Cycle

    Given a linked list, determine if it has a cycle — without using extra memory.

    nodes (index 3's "next" wraps back to index 1 — that's the cycle)

    The trick: two pointers, slow moves one step at a time, fast moves two. If there's no cycle, fast reaches the end first. If there IS a cycle, fast eventually laps slow and they land on the same node — that's Floyd's cycle detection, O(1) extra space.

    Reorder List

    Reorder L0→L1→…→Ln into L0→Ln→L1→Ln-1→… in place.

    first half
    second half, reversed
    result — weaving the two together

    The trick: three steps — find the middle (slow/fast pointers), reverse the second half, then merge the two halves by alternating nodes from each. Three problems you already know, chained together.

    Day 8 of 14

    Trees I

    Recursion is the native language of trees — most solutions are "handle this node, trust the recursion for its children."

    currently examining match / resolved seen / checked

    Concept: recursion as delegation

    Tree problems almost always have the same shape: assume the recursive call already correctly solves the subtree, and figure out how to combine its result(s) with the current node. "Invert this tree" becomes "invert my children, then swap them onto myself." You never have to think about the whole tree at once — just one node and what its children promise to hand back.

    This is a base-case-plus-combine pattern: define what happens at null (usually a trivial answer — 0, true, None), define what a leaf does, then trust the recursion for everything below the current node. Depth-first recursion naturally explores the full height of the tree before combining, using the call stack as implicit O(h) space, where h is the tree's height (O(log n) balanced, O(n) worst case for a degenerate chain).

    Comparing two trees, or searching for a subtree, is the same idea one level up: define "are these two nodes/subtrees equal," then use that as a building block for "does this tree contain that pattern anywhere."

    Reach for tree recursion when: the problem is naturally defined in terms of "a node and its subtrees" — depth, symmetry, equality, containment. Interview follow-up to expect: can you do it iteratively with an explicit stack instead of the call stack? (Useful when recursion depth risks a stack overflow on very unbalanced trees.)

    Invert Binary Tree

    Flip a binary tree into its mirror image.

    The trick: at every node, swap its left and right children, then recurse into both. Order doesn't matter — swap-then-recurse and recurse-then-swap both work, since every node gets visited exactly once either way.

    Maximum Depth of Binary Tree

    Return the number of nodes along the longest path from root to a leaf.

    The trick: a leaf's depth is 1. Every other node's depth is 1 + the deeper of its two children's depths. Compute children first (post-order), then combine — classic bottom-up recursion.

    Same Tree

    Given two binary trees, return true if they're structurally identical with the same node values.

    tree p
    tree q

    The trick: walk both trees together, node by node. Two nodes match if both are null, or both exist with equal values and their left/right subtrees also match — recursively.

    Subtree of Another Tree

    Given two trees, return true if subRoot appears as an exact subtree anywhere inside root.

    root — candidate highlighted
    subRoot — looking for this shape

    The trick: try every node in root as a candidate root. At each one, run the Same Tree check against subRoot. The first candidate where it matches means subRoot is in there.

    Day 9 of 14

    Trees II + Tries

    Breadth-first traversal, tree invariants, and tries — a tree shape specialized for prefixes.

    currently examining match / resolved seen / checked

    Concept: BFS vs DFS, and the trie

    Day 8's recursion was depth-first: go all the way down one branch before backing out. Breadth-first search instead explores level by level, using a queue instead of the call stack — pull a node, push its children, repeat. That's the only way to naturally answer "what's at depth k" or "shortest path in an unweighted structure" questions, because BFS visits everything at distance d before anything at distance d+1.

    Validating a BST is DFS with a twist: instead of just combining child results, you thread a valid (low, high) range down through the recursion — every node in a valid BST must fall strictly between the bounds set by its ancestors, not just be greater than its immediate parent.

    A trie (prefix tree) is a different data structure for a different question: not "does this tree have a property" but "is this string, or some prefix of it, in my set of strings." Each node is a hashmap of child-character → child-node; walking a word one character at a time is O(k) for a word of length k, independent of how many words are stored — much better than checking a word against every string in a set.

    Reach for BFS when: you need shortest-path/level-by-level behavior on a tree or graph. Reach for a bounded DFS when validating a global tree property (like BST-ness) that a naive parent-only check would miss. Reach for a trie when you're doing repeated prefix lookups/autocomplete over a fixed dictionary of words — the classic follow-up is "now support wildcard search," solved with DFS over the trie that branches on '.'.

    Binary Tree Level Order Traversal

    Return the tree's node values level by level, left to right.

    queue

    levels collected so far

    The trick: BFS with a queue. Process the queue one full level at a time — record its size first, pop exactly that many nodes, push their children for the next round.

    Validate Binary Search Tree

    Return true if the tree satisfies the BST property everywhere, not just at each parent-child pair.

    The trick: checking a node against just its immediate parent isn't enough — a node deep in the left subtree must be less than every ancestor above it, not just its direct parent. Carry a (low, high) valid range down through the recursion and narrow it at each step.

    Lowest Common Ancestor of a BST

    Given a BST and two nodes p and q, find their lowest common ancestor.

    The trick: use the BST ordering instead of searching blindly. If both p and q are smaller than the current node, the answer is in the left subtree; if both are bigger, it's in the right. The moment they split (or one equals the current node), you've found the LCA.

    Implement Trie (Prefix Tree)

    Build a data structure supporting insert, search (exact word), and startsWith (prefix) in O(word length).

    operations

    path walked this operation

    The trick: each node is a dictionary of child letters, plus an end-of-word flag. Insert walks/creates a node per character; search walks and requires the end flag on the last node; startsWith walks but doesn't care about the end flag.

    Heap / Priority Queue

    A binary heap keeps "the most important element" at the root in O(1) peek time, and restores that property in O(log n) after any push or pop — the structure behind every "kth largest/smallest" and "k closest" problem.

    currently examining / just moved root of the heap seen / checked

    Concept: the heap invariant

    A binary heap is a complete binary tree stored flat in an array: for index i, children live at 2i+1 and 2i+2. The heap invariant says every parent has priority over its children (smaller, for a min-heap; larger, for a max-heap) — so the root, index 0, is always the most extreme element, readable in O(1).

    Push appends to the end of the array, then "sifts up" — swaps with its parent while it violates the invariant — in O(log n) since the tree has O(log n) levels. Pop removes the root, moves the last element into its place, and "sifts down" — swaps with whichever child has priority — again O(log n).

    The classic "top k" trick: to find the k largest elements of n, don't sort all of n (O(n log n)). Keep a min-heap of size k instead — push every element, and pop whenever the heap exceeds size k. The heap always holds the k largest seen so far, and its root is the smallest of those k (i.e. the kth largest overall). Total cost: O(n log k), better than a full sort when k is small.

    Reach for a heap when: you see "kth largest/smallest", "k closest/most frequent", or you need repeated access to a running min/max while the underlying set keeps changing (a streaming median, a scheduler, Dijkstra's algorithm). A common follow-up: can you avoid a full sort? — a size-k heap almost always beats sorting everything when k ≪ n.

    Kth Largest Element in a Stream

    Design a class that, given an integer k and an initial stream of numbers, supports add(val) and always returns the kth largest element seen so far.

    min-heap of the k largest values seen — root is the kth largest (k = 3)

    The trick: keep a min-heap capped at size k. Any value that makes it into the heap and survives is one of the k largest so far; the heap's root — the smallest of those k — is exactly the kth largest. Push, then pop if you're over capacity: O(log k) per add instead of re-sorting everything.

    Last Stone Weight

    Stones have weights. Repeatedly smash the two heaviest together: if equal, both vanish; otherwise the lighter's weight is subtracted from the heavier, and the remainder goes back in. Return the weight of the last stone left (0 if none).

    max-heap of stone weights

    The trick: "repeatedly grab the two largest" is exactly what a max-heap is for — pop twice, push the difference if any, repeat until at most one stone remains. Every operation is O(log n), for O(n log n) total instead of re-scanning for the max pair each round.

    K Closest Points to Origin

    Given a list of points on the plane and an integer k, return the k points closest to the origin (0, 0).

    max-heap of squared distances, capped at k = 2 — cells show distance, not the point

    The trick: same size-k-heap pattern as Kth Largest in a Stream, just keyed by squared distance instead of the value itself (no need for an actual square root — it doesn't change the ordering). Keep a max-heap of size k; anything that survives being pushed is among the k closest.

    Kth Largest Element in an Array

    Given an unsorted array and an integer k, return the kth largest element — not the kth distinct one.

    min-heap capped at size k = 2 — root ends up the answer

    The trick: identical shape to the streaming version, just fed the whole array at once instead of one value at a time — O(n log k). (A quickselect partition averages O(n) time but is trickier to get right under pressure; the heap approach is the safer default to reach for first.)

    Backtracking

    Explore a decision tree depth-first: choose, recurse, and — critically — undo the choice on the way back out so the next branch starts clean.

    currently chosen / visiting recorded result visited on this path

    Concept: choose, explore, un-choose

    Backtracking is DFS over a tree of decisions rather than a tree of nodes. At each step you pick one option, recurse as if that pick were permanent, and when the recursion returns — whether it found something or hit a dead end — you undo the pick before trying the next option. That undo step is the entire trick: without it, state from one branch would leak into a sibling branch that never should have seen it.

    The three-beat rhythm — choose / explore / un-choose — appears identically whether you're building subsets, combinations, permutations, or a path through a grid. What changes between problems is only: what counts as a valid choice at this point, what marks a complete answer, and what state needs undoing (a used[] flag, a running sum, a visited cell).

    Complexity is inherently exponential — you're enumerating a search space, not shortcutting it — so the goal is to prune early (stop recursing the moment a partial path can't possibly succeed) rather than to avoid the exponential shape entirely.

    Reach for backtracking when: the problem says "all possible ...", "every combination/permutation/arrangement", or asks you to find a path/placement satisfying constraints (word search, N-Queens, Sudoku). Interview follow-up to expect: "how would you prune?" — sorting input to fail fast, or an early bound check (remaining sum, remaining cells) before recursing.

    Subsets

    Given an array of unique integers, return all possible subsets (the power set).

    current path (nums = [1, 2, 3])

    subsets recorded so far

    The trick: every prefix of the recursion is itself a valid subset — record the path at every node of the decision tree, not just at the leaves. Each element is either in the path or not, so recursing "from index i onward" (never revisiting earlier indices) naturally generates each subset exactly once, in 2ⁿ total leaves.

    Combination Sum

    Given distinct candidates and a target, return every combination that sums to target. The same number may be reused as many times as needed.

    current path (candidates = [2, 3, 6, 7], target = 7)

    combinations recorded so far

    The trick: allowing reuse just means the recursive call starts from the same index again instead of index+1. Track the remaining target as you go so a leaf is reached exactly when remaining hits 0 — and prune immediately (skip, don't even recurse) the moment a candidate would overshoot.

    Permutations

    Given an array of distinct integers, return all possible permutations (every ordering).

    current path (nums = [1, 2, 3])

    permutations recorded so far

    The trick: unlike subsets, order matters and every element must appear exactly once — so instead of an index cursor, track a used[] flag per element and try every not-yet-used element at each position. A leaf is reached when the path's length equals the input length.

    Word Search

    Given a 2D board of letters and a word, return true if the word can be traced through adjacent (up/down/left/right) cells, each used at most once.

    board — searching for "ABCCED"

    The trick: DFS from every starting cell, matching the word one character at a time; mark a cell visited before recursing into its neighbors, and un-mark it on the way back out so a later, different path can reuse that cell. The moment a neighbor's letter doesn't match the next required character, prune — don't recurse at all.

    Graphs

    Grids, adjacency lists, and directed edges are all the same object underneath: nodes and connections. DFS/BFS traversal, with a visited set to avoid infinite loops, solves almost everything here.

    currently visiting resolved / in the answer visited on this pass

    Concept: traversal with a visited set

    A graph is just nodes plus edges — a 2D grid is a graph where each cell is a node connected to its (up to 4) neighbors; an adjacency list is the same idea written explicitly. Every algorithm here is a traversal (DFS or BFS) that never revisits a node, tracked with a visited set/array, so the walk always terminates even when the graph has cycles.

    DFS (recursive, or an explicit stack) is the natural fit for "explore everything connected to this node" — flood fill, connected components, cycle detection. BFS (a queue) is the natural fit for "shortest path / fewest steps" in an unweighted graph, and for "process everything reachable, level by level."

    Cycle detection needs one more idea beyond plain visited/unvisited: a third state, "currently being explored" (in progress, still on the call stack). If a DFS reaches a node that's already in progress, that's a back-edge — a cycle. A node that's fully finished and popped off the stack is safe to revisit from anywhere else without re-exploring it.

    Reach for graph traversal when: the problem involves a grid (flood fill: islands, water flow, regions), explicit nodes/edges (clone a graph, detect a cycle, topological order), or "is X reachable from Y". Interview follow-up to expect: "what if the graph is very large / very deep?" — BFS avoids recursion-depth issues that a naive recursive DFS can hit on a long chain.

    Number of Islands

    Given a 2D grid of '1' (land) and '0' (water), return the number of islands — connected groups of land, horizontally/vertically adjacent.

    grid

    The trick: scan the grid; the moment you find unvisited land, that's a brand-new island — flood-fill (DFS/BFS) outward from it marking every connected land cell visited, so the outer scan never counts it again. Total work is O(rows·cols): every cell is visited at most once.

    Clone Graph

    Given a reference node in a connected undirected graph, return a deep copy (clone) of the graph.

    graph — node : neighbors — 1:[2,4] 2:[1,3] 3:[2,4] 4:[1,3]

    clone map — original node → cloned?

    The trick: DFS (or BFS) from the given node, keeping a hashmap from original node → its clone. Before recursing into a neighbor, check the map — if it's already cloned, just wire up the edge to the existing clone instead of recursing again, which is exactly what stops infinite loops on a cyclic graph.

    Course Schedule

    Given numCourses and a list of prerequisite pairs [course, prereq], return true if it's possible to finish all courses (i.e. the prerequisite graph has no cycle).

    course states — 0=unvisited, 1=visiting, 2=done (prereqs: 0→1, 0→2, 1→3, 2→3)

    DFS recursion stack

    The trick: this is cycle detection on a directed graph. DFS with three states per node — unvisited, visiting (on the current call stack), done. Hitting a "visiting" node again means you've looped back onto your own path: a cycle, so the courses can't all be finished. Hitting a "done" node is fine — that subgraph was already proven safe.

    Pacific Atlantic Water Flow

    Given a grid of heights, with the Pacific bordering the top/left edges and the Atlantic bordering the bottom/right edges, return every cell from which water can flow to both oceans (flowing to equal-or-lower neighboring cells).

    heights — flood-filling in reverse from each ocean's border

    The trick: don't simulate water flowing from every cell (that's O((rows·cols)²)). Flip the direction: flood-fill inward from each ocean's border, moving to a neighbor only if its height is ≥ the current cell's (i.e. water there could have flowed down to here). Run it once per ocean, then intersect the two reachable sets — O(rows·cols) total.

    1-D Dynamic Programming

    Break a problem into overlapping subproblems, solve the small ones first, and build the answer up from a table of results you never have to recompute.

    cell being computed earlier value it depends on seen / checked

    Concept: memoize the overlapping subproblems

    Dynamic programming applies when a problem has two properties: an optimal solution is built from optimal solutions to smaller versions of itself (optimal substructure), and those smaller versions repeat across different branches of a naive recursion (overlapping subproblems). Climbing n stairs reduces to climbing n-1 and n-2 stairs; without caching, a naive recursive solution recomputes the same smaller cases exponentially many times.

    1-D DP means the subproblems are indexed by a single integer — usually "the answer considering only the first i elements/steps/dollars." You fill a table dp[0..n] left to right, where dp[i] is computed purely from a handful of earlier entries (often just dp[i-1] and dp[i-2], or a min/max over several prior entries). Once the recurrence is right, the code is often just a single loop.

    Time drops from exponential (naive recursion) to O(n) or O(n·k) (one pass through the table, k = choices considered per cell); space is O(n) for the full table, though many of these can be optimized to O(1) by keeping only the last couple of values — since dp[i] only ever looks a fixed, small distance backward.

    Reach for 1-D DP when: the problem asks for a count, a min/max, or a yes/no over "the first i" something, and you can express dp[i] in terms of dp[i-1], dp[i-2], etc. A frequent follow-up: "can you reduce the space?" — if dp[i] only depends on a constant number of previous entries, keep just those instead of the whole array.

    Climbing Stairs

    You can climb 1 or 2 steps at a time. Given n stairs, how many distinct ways can you reach the top? (n = 5)

    dp[i] = number of ways to reach step i

    The trick: reaching step i means your last move was either a 1-step from i-1 or a 2-step from i-2, so dp[i] = dp[i-1] + dp[i-2] — this is just Fibonacci wearing a different hat. Recognizing that "n choices for the last move" shape is most of the work in DP problems.

    House Robber

    Given nums = [2, 7, 9, 3, 1], the money at each house, find the max you can rob without robbing two adjacent houses.

    dp[i] = max money robbable from houses 0..i

    The trick: at house i you have exactly two options — skip it (carry forward dp[i-1]) or rob it (dp[i-2] + nums[i], since the previous house is now off-limits). dp[i] is just the better of those two, so dp[i] = max(dp[i-1], dp[i-2] + nums[i]).

    Coin Change

    Given coins = [1, 2, 5] and amount = 11, return the fewest coins needed to make that amount (or -1 if impossible).

    dp[i] = fewest coins to make amount i (∞ = not yet reachable)

    The trick: dp[0] = 0 (zero coins for zero amount). For every amount i and every coin c ≤ i, dp[i] can be reached by using one more coin than dp[i-c] needed — take the best coin: dp[i] = min over coins c of (dp[i-c] + 1). This is unbounded-knapsack shaped: each coin can be reused any number of times.

    Longest Increasing Subsequence

    Given nums = [10, 9, 2, 5, 3, 7, 101, 18], return the length of the longest strictly increasing subsequence (not necessarily contiguous).

    dp[i] = length of the longest increasing subsequence ending at index i

    The trick: for each index i, look back at every earlier index j; if nums[j] < nums[i], index i could extend that subsequence, giving a candidate length dp[j] + 1. dp[i] is the best candidate over all valid j (or 1, if none extend it). O(n²) here; a patience-sorting + binary search variant gets this down to O(n log n).

    Intervals + Greedy + Review

    Sort first, then make the locally obvious choice at each step and never look back — that's greedy, and intervals are its home turf. We close with a cheat sheet across all 14 days.

    currently examining kept / merged / best-so-far discarded / seen

    Concept: sort, then decide greedily

    A greedy algorithm makes the choice that looks best right now and never revisits it — no backtracking, no exploring alternatives. That only produces a correct (not just plausible) answer when the problem has the right structure: usually, that sorting the input by some key turns the decision at each step into an obviously-correct local one.

    Interval problems are the canonical case: sort by start time and overlapping intervals become adjacent, so merging is a single linear scan. Sort by end time and "keep the interval that frees up the earliest" becomes provably optimal for minimizing removals — because an interval ending earlier can never make future choices worse than one ending later.

    Kadane's algorithm for maximum subarray is greedy in a different way: it never explores "what if I'd started the subarray somewhere else" — it just tracks a running sum, and resets to 0 the instant that running sum goes negative (a negative prefix can never help a future subarray, so it's always correct to drop it).

    Reach for greedy when: the problem is about intervals (merge, insert, remove for non-overlap, meeting rooms), or you can argue "the locally best choice never hurts the globally best answer" — and you can usually verify greedy is safe by trying to construct a counterexample; if you can't, it's a strong signal greedy works. Interview follow-up: "prove your greedy choice is safe" — be ready to argue it, not just claim it.

    Insert Interval

    Given a sorted, non-overlapping list of intervals and a new interval, insert it, merging as needed. intervals = [[1,3],[6,9]], newInterval = [2,5].

    result so far

    The trick: three simple passes over the sorted input — copy every interval that ends before the new one starts untouched; while an interval overlaps the (possibly already-growing) new interval, absorb it by widening the new interval's bounds; then copy the rest untouched. One linear scan, no re-sorting needed.

    Merge Intervals

    Given a list of intervals, merge all overlapping ones. intervals = [[1,3],[2,6],[8,10],[15,18]].

    merged result so far

    The trick: sort by start time — now any two intervals that overlap must be adjacent in the sorted list. Walk once: if the next interval starts before (or exactly when) the last merged one ends, extend the last merged interval's end; otherwise it starts a fresh, disjoint group.

    Non-overlapping Intervals

    Given a list of intervals, return the minimum number to remove so the rest don't overlap. intervals = [[1,2],[2,3],[3,4],[1,3]].

    intervals, in the order examined (sorted by end time)

    The trick: sort by end time, not start time — greedily keep whichever interval ends earliest, since that leaves the most room for everything after it. Any interval that starts before the last kept interval's end must be removed; count those removals instead of trying to choose which to keep first.

    Maximum Subarray (Kadane's)

    Given nums = [-2, 1, -3, 4, -1, 2, 1, -5, 4], find the contiguous subarray with the largest sum, and return that sum.

    nums

    running sum vs best sum seen

    The trick (Kadane's algorithm): keep a running sum as you scan; the instant it goes negative, it can only drag down any subarray that includes it, so reset it to 0 and start fresh from the next element. Track the best running sum seen at any point — that's the answer. One pass, O(1) space.
